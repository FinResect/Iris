# 摄像头延迟与帧率优化分析

> 对比对象：`iris_ws/src`（当前） vs `Ti60F225_DemoBoard_v4/10_Ti60f225_sc431hai2hdmi_demo`（官方参考）
> 传感器：SC431HAI（MIPI CSI-2 RAW10 4-lane，J4）
> 显示：HDMI TMDS 1080p60

---

## 0. 结论摘要

- **帧率瓶颈是传感器 30 fps，不是带宽**。MIPI 占用 11%、DDR3 占用 12%，都有大量富余。
- **延迟 95% 来自 3 个帧级阶段**：曝光（被设成整帧积分）+ DDR bank 整帧写完才发布 + 显示 V 相位等待。像素级流水合计仅 ~0.5 ms。
- **`axi_atype_bridge` 整笔串行（写优先）曾是最大的架构隐患**——已验证控制器本身支持并发读写，串行化是 bridge 自找的，**已改为读优先 2:1 地址 mux 并通过构建**（详见 §4.1）。
- 传感器 I2C ROM 与官方 **逐项相同**，debayer / frame_buffer 子模块大部分 **逐字节相同**；差异集中在 DDR 控制器桥接、bank 策略、显示时钟、启动门控四处。

```

```

## 2. 帧率诊断

### 2.1 带宽都不是瓶颈

| 资源 | 需求 | 容量 | 占用 |
|---|---|---|---|
| MIPI CSI-2 | 1080p30 RAW10 = 249 Mbps | 560 Mbps/lane × 4 = 2.24 Gbps | **11%** |
| DDR3 | 写 62.2 + 读 124.6 = 187 MB/s | 16-bit DDR3-800 = 1.6 GB/s | **12%** |
| AXI fabric | 同上 | 100 MHz × 128-bit = 1.6 GB/s | 12% |

### 2.2 传感器出帧率 30 fps 是硬顶

证据：`iris_ws/src/ddr/fb/ddr_buffer.v:216-220`

```
// Write-driven bank latching (3 banks).
//   The reader always reads the most recently completed write bank; the writer
//   advances to the next bank only after a full frame (wr_sw).  This removes the
//   demo's wr_sw/rd_sw alternation, which mis-aligns when the read rate (60 fps)
//   differs from the write rate (30 fps).
```

显示侧：`74.375 MHz / (2200 × 1125) = 60.09 fps`（CEA 1080p60，`top.v:315-322`）。
30 fps 内容在 60 Hz 上每帧显示 2 次 → 顿挫感。

### 2.3 传感器寄存器问题

ROM 位置：`iris_ws/src/mipi/sc431hai_i2c_rom.v`（161 项，与官方 `i2c_master_reg_rom` 的 SC431HAI 块 **0 diff**）。

| 问题 | 证据 | 后果 |
|---|---|---|
| **VTS/HTS 未编程** | `0x320C–0x320F` 不在 161 项表内，VTS 用默认 `0x05DC` = 1500（`docs/SC431HAI_硬件设计指南.md:284`） | 帧率被默认帧长锁死 |
| **曝光被设成最大值** | `0x3e00/01/02` = `0x00/0xBA/0xD0` → `{0x3e00[3:0], 0x3e01, 0x3e02[7:4]}` = `0x0BAD` = **2989 半行**；上限 `2*VTS − 11` = `2×1500−11` = **2989**（指南 `:304`） | **整帧积分 99.6%** → 严重运动模糊，这是"感知延迟"的最大来源 |
| SC431HAI 无 AEC/AGC | 指南 `:298` | 必须手动给合理曝光，不能指望自动 |
| 曝光更新延迟 | 指南 `:299`："第 N 帧写入，第 N+2 帧生效" | 控制延迟 2 帧（非流水延迟） |

帧率公式（指南 `:360-361`）：`fps = 1 / (line_time × VTS)`，`line_time = 1/(HTS 相关像素时钟)`。

## 3. 延迟预算（光子→屏幕 ≈ 85–100 ms）

| # | 阶段 | 粒度 | 延迟 | 代码位置 |
|---|---|---|---|---|
| 1 | **曝光** | 帧 | **33 ms** | ROM `0x3e00-02` 拉满 |
| 2 | 读出 + CSI 解码 + clipper + 打包 | 行/像素 | ~0.05 ms | `top.v:215-227`, `mipi_rx.v` |
| 3 | ser2par + WR FIFO + AXI 写本像素 | 字 | ~0.01 ms | `ser2par_32_128_v1.v`, `ddr_wr_buffer.v` |
| 4 | **等整帧写完才发布 bank** | **帧** | **0–29 ms** | `ddr_wr_buffer.v:302` → `ddr_buffer.v:244` |
| 5 | **等下一次显示 V 才锁存读地址** | **帧** | **0–16.7 ms** | `data_tx.v:425` → `ddr_rd_buffer.v:83` |
| 6 | DDR 读 + RD FIFO 预取 | 行 | ~0.5 ms | `ddr_rd_buffer.v` |
| 7 | 显示扫描到该像素 | 帧位置 | 0.6–16.6 ms | |
| 8 | debayer 2 行缓存 + 3×3 核 | 行 | ~0.15 ms | `line_buffer.v:87-111`, `raw_to_rgb.v` |
| 9 | 2→1 FIFO + 输出寄存器 + TMDS 编码 | 像素 | ~0.05 ms | `top.v:403-458`, `encode.v` |
| | **像素级流水合计（2+3+8+9）** | | **~0.5 ms（可忽略）** | |

**帧级延迟 3 项（#1 曝光 + #4 bank 整帧发布 + #5 显示 V 相位）占 95%。**

### 3.1 bank 发布机制（帧级延迟的来源）

`iris_ws/src/ddr/fb/ddr_buffer.v:215-249`：

```verilog
localparam [31:0] BANK_STRIDE = 32'h001FB000;   // 1920*1080*1 rounded up to 4 KB
// ...
always @(posedge axi_clk or negedge axi_clk_rst_n) begin
    if (!axi_clk_rst_n) begin
        wr_bank     <= 2'd0;
        rd_bank     <= 2'd1;
        frame_ready <= 1'b0;
    end else if (wr_sw) begin          // wr_sw = 本帧最后一个 AXI burst
        rd_bank     <= wr_bank;        // 发布刚写完的 bank
        wr_bank     <= (wr_bank == 2'd2) ? 2'd0 : (wr_bank + 1'b1);
        frame_ready <= 1'b1;
    end
end
```

- 一个 bank 只有在**完整帧写完**后才可读 → 强制 1 帧存储延迟。
- 读侧在**下一次显示 V** 才锁存 `rd_start_addr` → 再加 0–1 显示帧相位延迟。
- 三缓冲实际只带来 **1–2 个帧槽**延迟（不是 3 帧）：1 帧（等写完）+ 0–1 帧（读相位）+ 0–1 帧（扫描到该像素）。

### 3.2 三缓冲策略

当前是"最新帧锁存"：写指针永不等待，读指针永远拿最新完整帧。延迟最低，但 **写 fps > 读 fps 时写会套圈正在被读的 bank → 撕裂**。
30 fps 写 / 60 fps 读（每帧显示两次）时安全；提到 60 fps 后必须加读占用锁。

### 4.1 `axi_atype_bridge` 串行化：已定位、已修复

#### 原实现的问题

旧 `axi_atype_bridge.v` 的注释声称：

```
// Because the efx_ddr3_axi controller is driven strictly sequentially by
// its own reference host (memory_checker_axi: write -> wait bvalid ->
// read -> wait rlast), this bridge additionally serializes WHOLE
// transactions.
```

状态机：`S_IDLE → S_AW → S_AW_REL → S_WAIT_WR(等 bvalid) → S_IDLE → S_AR → S_AR_REL → S_WAIT_RD(等 rlast) → S_IDLE`，
且 `S_IDLE` 中 `if (s_awvalid)` 优先于 `s_arvalid` → **写绝对优先**。

显示读侧缓冲只有 RD FIFO 1024×128b（16 KB ≈ 8.5 行）+ `data_tx` 行 FIFO 1024×16b（**半行**）。一次读 burst 被写 burst + B 响应堵住就可能欠载。

#### 验证结论：控制器本身支持并发，串行化是 bridge 自找的

**证据 1 — 控制器内部是双地址队列 + outstanding 计数器**（`outflow/iris_ws.map.v`，加密 RTL 的层次信号名在综合后暴露）：

| 网表信号 | map.v 行 | 含义 |
|---|---|---|
| `r_aw_state[3:0]` **和** `r_ar_state[3:0]` | `:775, 798` | 两个独立地址 FSM |
| `u_wr_addr_fifo` **和** `u_rd_addr_fifo` | `:1058, 1066` | 两个独立地址队列（各 32 深） |
| `r_wr_b_count[8:0]` | `:799` | 9 位"未完成写响应"计数器 |
| `r_rlast_cnt[15:0]` | `:774` | 16 位"未完成读"计数器 |
| `top_mc/fifo_aw` **和** `top_mc/fifo_ar` | `res.csv:195, 198` | 内部存储控制器也是双队列 |

**9 位 outstanding 写计数器 + 16 位 outstanding 读计数器，不可能存在于"一次只能一笔事务"的控制器里。**

**证据 2 — 注释引用的 `memory_checker_axi` 在整个工作区不存在**（0 处源码）。那句话是推测，不是依据。

**证据 3 — 本工程自己的主机从不串行化**：`ddr_wr_buffer.v:306-373` 写 FSM 在 `wlast & wready` 就返回 idle，**从不等 `bvalid`**（`bready=1'b1`，`bvalid` 未使用）；`ddr_rd_buffer.v:249-320` 读 FSM 可 AR 背靠背。

**真实硬件限制**：`efx_ddr3_axi.sv:90-98` 只有一条地址通道 `axi_a*` + `axi_atype`，**每拍只能传 1 个地址**（切方向 0~1 拍）。不是"整笔 burst + 响应"。

#### 修复（已完成）

`axi_atype_bridge.v` 重写为**读优先 2:1 地址 mux**，删除整个状态机：

```verilog
wire sel_ar = s_arvalid;                 // 读优先
wire sel_aw = s_awvalid & ~s_arvalid;
assign s_awready = sel_aw & m_aready;
assign s_arready = sel_ar & m_aready;
assign m_avalid  = sel_aw | sel_ar;
assign m_atype   = sel_aw;               // 1=write, 0=read
// m_aid / m_aaddr / m_alen / m_asize / m_aburst / m_alock = 二选一 mux
```

读优先的依据：显示读是实时负载（`data_tx` 只有半行 FIFO），写侧有 8.5 行 WR FIFO 且 30 fps 源远慢于总线。读侧地址占用率 <0.1%（1 地址 / 14.8 µs @ 100 MHz），写不会饿死。

端口表一字未改 → `top.v` / `iris_ws.xml` / `peri.xml` / GUI **零改动**。

#### 验证结果

| 项 | 改前 | 改后 |
|---|---|---|
| 资源（`outflow/iris_ws.res.csv:171`） | 40 FF / 58 LUT | **0 FF / 1 LUT** |
| 状态机 `S_WAIT_*` / `S_AW_REL` / `S_AR_REL` | 存在 | **0 处**（已消除） |
| 控制器内部 `r_aw_state`/`r_ar_state`/`r_wr_b_count`/`r_rlast_cnt` | 57 处 | **57 处**（未受影响） |
| 构建 | — | map / interface / pnr / pgm 全 **PASS** |
| 时序余量（`outflow/iris_ws.timing.rpt`） | — | 最小 slack **+3.804 ns** |
| mux 真值表（T1–T7，25 项断言） | — | 全通过（含读优先、满速率、`m_avalid` 不依赖 `m_aready`） |

`bvalid`/`rlast` 等端口保留（top.v 接线不变）但不再使用——响应跟踪由控制器内部 outstanding 计数器完成。

### 4.2 bank 步长差异

| | 官方 | 当前 |
|---|---|---|
| 公式 | `FRAME_LEN = MAX_VID_WIDTH*MAX_VID_HIGHT*VID_DATA_WIDTH/8 + 0x200` | `BANK_STRIDE = 32'h001FB000` |
| 计算 | `960*1080*4 + 512 = 0x3F3200`（约 2× 真实帧） | `1920*1080*1 = 0x1FB000`（恰好 1 帧） |
| 真实帧大小 | 1920 px × 1 B × 1080 = 2,073,600 B = `0x1FA800` | 相同 |
| 保护带 | ~2 MB 松弛 | **0**（仅 4 KB 对齐余量 0x800） |

官方的 `MAX_VID_WIDTH=960` 配 `VID_DATA_WIDTH=32` 是把 2px 字宽和 4B 字宽重复计算了，浪费但安全。当前压到恰好 1 帧，clipper/vsync 任何竞态多写一个 de-beat 就会踩进下一 bank。

## 5. 优化方案（按优先级）

### P0 — 止血（半天–1 天，低风险）

| # | 动作 | 位置 | 说明 |
|---|---|---|---|
| 1 | **曝光降下来** | `sc431hai_i2c_rom.v:137-139` | `0x3e00/01/02` 从 `0x00/0xBA/0xD0`（=上限 2989 半行）改为如 `0x00/0x01/0x00` → `0x0100` = 128 半行 ≈ 64 行（约 4% 帧长）。消除运动模糊 = 消除主要"感知延迟" |
| 2 | **显式编程 HTS/VTS** | `sc431hai_i2c_rom.v` 增补 `0x320C-0x320F` | 不再用默认 `0x05DC`；VTS 同时也是提帧率的旋钮 |
| 3 | `data_tx.frame_en` 改接 `rd_frame_en_r1` | `frame_buffer.v:329` | 对齐官方 `:324`，消除启动期欠载 |
| 4 | `wr_start` 加 `frame_stable` 门控 | `frame_buffer.v:201` | 对齐官方 `:196` |
| 5 | Bank 步长加保护带 | `ddr_buffer.v:222` | `0x1FB000` → `0x1FC000`（+4 KB）或恢复官方 `+0x200` |
| 6 | 修 `frame_info_det` 位宽 bug | `frame_info_det.v:93` | `frame_len_d0 <= frame_end_r0` → `<= frame_cnt`（取消注释），让 `frame_stable` 真正做帧长校验 |
| 7 | bank 环加读占用锁 | `ddr_buffer.v:239-248` | `wr_bank` 前进时若下一 bank == `rd_bank` 则跳过或挂起写，为 P1 提帧率防撕裂 |

### P1 — 提帧率（1–3 天）

| # | 动作 | 说明 |
|---|---|---|
| 8 | **先测量** | 加 UART/LED 帧计数器，实测 fps 与 HTS×VTS（目前全是推算） |
| 9 | 三条提频路径 | 见下表 |

| 路径 | 做法 | 预期 | 代价 |
|---|---|---|---|
| **A. 裁到 1280×720**（推荐） | `0x3208/09 = 0x0500`，`0x320A/0B = 0x02D0`，VTS 最小 ~800 | 当前 PCLK 下 **~50–56 fps** | 改 4 个寄存器；显示再放大到 1080p |

### P3 — 赛题配套提醒

- 赛题硬指标是 **640×480 风格化 ≥15 fps**（`赛题一_…任务分级…md:67`），HDMI 最低 720p60 或 1080p30（`:61`）。
- **摄像头不是赛题瓶颈**。CNN 的 DSP（仅 160 个）与中间特征图访存才是（同文件 `:164, :262`）。
- P0+P1 做完后给 CNN 留出 60 fps 输入余量，允许 CNN 抽帧到 15 fps 而不丢采集帧。
- 若做 L5b（720p@30，`:98`），P1 路径 A 的 1280×720 正好是入口。

## 6. 优化前后延迟预算对照

| | 原始 | **当前（P2-10 已做）** | P0+P1 | +P2(12) | +P2(11 直通) |
|---|---|---|---|---|---|
| AXI 读写 | 整笔串行、写优先 | **并发、读优先** | 并发、读优先 | 并发、读优先 | 并发、读优先 |
| 显示读被写阻塞 | 有（~2–3 µs/burst） | **无** | 无 | 无 | 无 |
| 传感器 fps | 30 | 30 | 50–60 | 50–60 | 50–60 |
| 曝光 | 整帧（模糊） | 整帧（模糊） | 短曝光 | 短曝光 | 短曝光 |
| 数据延迟（曝光结束→屏） | ~45 ms | ~43 ms（消除读阻塞尖峰） | ~25 ms | **~5–10 ms** | **~0.05 ms** |
| 光子→屏 | ~85–100 ms | ~83–98 ms | ~50–60 ms | **~25–35 ms** | **~曝光 + 2 ms** |

> P2-10 消除的是**读被写阻塞的停顿尖峰**与**显示读欠载风险**（`data_tx` 半行 FIFO），稳态延迟只小幅下降。帧率与感知延迟的大头仍在 P0（曝光）和 P1（传感器 fps）。

## 7. 待确认的取舍

1. **优先目标**：先要"画面流畅不卡"（P1 提帧率），还是"动作跟手延迟低"（P2 降延迟），还是两者都要？
2. **分辨率**：为 60 fps 能否接受传感器输出 1280×720（再放大到 1080p 显示）？还是必须保持 1920×1080（那就走 PLL 重编，需要数据手册）？
3. **撕裂 vs 延迟**：能否接受"行粒度读出"的帧内时间梯度（上半屏新、下半屏旧）？还是必须整帧无撕裂？
4. **直通通路**：是否值得做 CSI→HDMI 直通（亚毫秒级数据延迟）？会多一条独立显示通路与 DDR/AI 通路并行。
